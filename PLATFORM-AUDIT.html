How to read this report

Findings are numbered 1..N for this repository and ordered by severity. Each finding also carries a stable Ref (P-xx for platform-wide issues, A-xx-nn for app-specific ones) that is identical in the reports written to the other five repositories, so the same issue can be tracked across apps. The "Also affects" line lists the sibling apps that share the finding and the severity it carries there. Evidence paths are relative to the repository root; line numbers refer to the working tree on 2026-09-28.

Method: static review of the six working trees, a diff of every "mirrored by hand" file against AppBase (component primitives, ThemeContext, theme-init.js, input.css token blocks, server error handlers, API clients), and a read of each Layout, route table, auth context and server entry point. Nothing was executed against a running instance; visual claims are inferred from code and are marked where confirmation in a browser would be prudent.

Findings

1

BudgetPlanner theme is stored under bp.* keys, so it never syncs with the rest of the platform

High
Ref A-BP-01 Category Logic/Bug Also affects AppBase (Low)

Impact. The design system contract is that dal.theme.mode and dal.ui.style (cookie + localStorage, optionally domain-scoped) carry color mode and UI style across every DAL app. BudgetPlanner renamed both to bp.theme.mode / bp.ui.style in ThemeContext and theme-init.js. A user who picks Light + Acrylic in Codex opens BudgetPlanner and gets Dark + Prism, and vice versa. VITE_SHARED_THEME_COOKIE_DOMAIN is honoured, so the app writes a .darkavianlabs.com cookie under the wrong name.

Evidence
  • BudgetPlanner/client/context/ThemeContext.tsx:34-40 SHARED_THEME_STORAGE_KEY = 'bp.theme.mode'; THEME_COOKIE = 'bp.theme.mode'; UI_STYLE_STORAGE_KEY = 'bp.ui.style'; UI_STYLE_COOKIE = 'bp.ui.style'
  • BudgetPlanner/public/theme-init.js:20,23,33,43,50 readCookie('bp.theme.mode') / localStorage 'bp.ui.style'

Recommendation. Rename the four constants back to dal.* in client/context/ThemeContext.tsx and public/theme-init.js (keep budgetplanner.theme.mode as the app-local fallback). Add a shared test to AppBase that asserts the key names so this cannot regress in any mirror.

2

Clerk sign-in/up routes lack the /* wildcard and render outside Layout

High
Ref A-BP-02 Category Logic/Bug Also affects this app only

Impact. SignInPage/SignUpPage use routing="path" with path="/sign-in". Clerk pushes sub-steps such as /sign-in/factor-one, /sign-in/factor-two and /sign-in/sso-callback. The routes are registered as exact paths (no /*), and there is no 404 route, so MFA and OAuth users land on a blank page mid-flow. AppBase AGENTS.md explicitly requires the wildcard. The routes are also mounted outside the Layout element, so the sign-in screen has no header, DalAppNav or shell backgrounds, unlike every sibling.

Evidence
  • BudgetPlanner/client/app/routes.tsx:47-48 <Route path={APP_PATHS.signIn} element={<SignInPage />} /> (outside <Route element={<Layout />}>)
  • BudgetPlanner/client/features/auth/SignInPage.tsx:23-24 routing="path" path="/sign-in"
  • AppBase/AGENTS.md:24 "Sign-in/up routes need /sign-in/* and /sign-up/* wildcards"

Recommendation. Register ${APP_PATHS.signIn}/* and ${APP_PATHS.signUp}/* inside the Layout route, as AppBase does.

3

Error presentation has no platform convention: toast vs banner vs inline vs native dialogs

High
Ref P-01 Category Error reporting Also affects AppBase (High), Codex (Medium), Outfitter (Medium), Armory (High), Sentinel (Medium)

In BudgetPlanner: No toast primitive or CSS at all; every outcome (save, invite, delete) is an inline paragraph that stays on screen. Success feedback is missing entirely for most mutations.

Impact. The same failure (a save that returns 4xx/5xx) is shown five different ways across the platform: a Toast pill, a LoadErrorBanner with Retry, a bare .error-msg div, inline text-danger text, an arbitrary text-[var(--color-danger)] span, or a browser alert(). Users learn a different mental model in every app, and error copy, placement and dismissal behaviour never match. This is the single largest coherence gap the audit found.

Evidence
  • Toast component present: AppBase, Codex, Sentinel only. Missing: BudgetPlanner (no .toast-pill CSS either), Outfitter (.toast-pill CSS exists but no component = dead CSS), Armory (custom ModBuilderToasts; .toast-pill lacks [data-interactive] and .toast-dismiss).
  • Codex: LoadErrorBanner (.error, role="alert", Retry) used 11x; text-danger 11x; Toast.
  • BudgetPlanner: inline text-danger 10x, no toast at all.
  • Outfitter: text-[var(--color-danger)] 7x and text-danger 2x (two conventions in one app), no toast.
  • Armory: text-danger 38x, .error-msg, text-red-300/90 (raw Tailwind palette), window.alert() 8x, confirm() 2x.
  • AppBase/Sentinel: .error-msg div only, no role.
  • BudgetPlanner/client/features/plan/PlanPage.tsx, EntrySheet.tsx, InvitePage.tsx, HomePage.tsx: {error ? <p className="text-danger ...">}
  • BudgetPlanner/client/styles/input.css: no .toast-pill definition (all five siblings have it)

Recommendation. Pick one primitive per situation and put it in AppBase so every app mirrors it: Toast (data-tone) for transient outcomes of a user action; an inline banner with Retry (Codex LoadErrorBanner is the best existing candidate) for failed page loads; field-level text under the input for validation. Give both role="alert" for error tone. Remove alert()/confirm() and use Modal + btn-danger for destructive confirmation (Codex ConfirmModal / BudgetPlanner delete modal already do this). Add the chosen components to the AGENTS.md component contract table.

4

Sign-in gate UX differs in every app (redirect, inline page, modal button, none)

Medium
Ref P-03 Category Workflow Also affects AppBase (Medium), Codex (Low), Outfitter (Medium), Armory (Medium), Sentinel (Medium)

Impact. Hitting a protected screen while signed out produces four different experiences: a hard redirect to /sign-in that forgets where you were (AppBase, Outfitter, Sentinel); a full "Sign in to use Codex" glass panel with return-to links (Codex); an inline card with a Clerk modal button (BudgetPlanner); or nothing at all until a 401 fires a "Session expired" modal (Armory). Return-to after login only works in Codex.

Evidence
  • BudgetPlanner/client/components/Layout/Layout.tsx:209-235 RequireAuth: <SignInButton mode="modal"> inside glass-surface (modal flow, unlike the path-routed pages elsewhere)

Recommendation. Standardise on one gate: an inline glass card inside Layout (keeps shell, backgrounds and nav) with Sign in / Create account actions and a return-to parameter, like Codex AccountRequiredPage. Ship it in AppBase as ProtectedRoute's signed-out branch. Keep Armory's session-expired modal as the shared 401 handler.

5

Two API-client lineages: /api/csrf vs /api/auth/csrf, and silent CSRF-token failure in the AppBase lineage

Medium
Ref P-04 Category Error reporting Also affects AppBase (Medium), Codex (Low), Outfitter (Medium), Armory (Low), Sentinel (Medium)

Impact. AppBase, BudgetPlanner, Outfitter and Sentinel share one utils/api.ts (cached string, endpoint /api/csrf). Codex and Armory share another (generation counter, in-flight de-duplication, endpoint /api/auth/csrf). In the AppBase lineage, when the token fetch fails getCsrfToken() returns "" and the mutation is still sent without a token; the server answers 403 and the user sees a generic failure instead of "could not reach server". The AppBase lineage also has no in-flight de-dupe, so N concurrent first mutations trigger N /api/csrf requests. The API path itself differs, so cross-app tooling and docs cannot assume one contract.

Evidence
  • BudgetPlanner/client/utils/api.ts:34-46 same silent-empty behaviour
  • BudgetPlanner/server/routes/api.ts:12 apiRouter.get('/csrf')

Recommendation. Adopt the Codex/Armory client (de-dupe + throw on missing token) as the AppBase version and mirror it. Pick one CSRF path (the AGENTS.md documents /api/csrf) and add a redirect or alias on the two servers that differ.

6

User menu lacks keyboard navigation and focus management in four apps

Medium
Ref P-07 Category Accessibility Also affects AppBase (Medium), Codex (Info), Outfitter (Medium), Armory (Info), Sentinel (Medium)

Impact. All six Layouts mark the header popup as role="menu" with role="menuitem" children, which promises Arrow/Home/End navigation, focus on open and focus return on close. Only Codex and Armory implement it. In AppBase, BudgetPlanner, Outfitter and Sentinel the menu opens without moving focus, arrow keys do nothing, and closing does not return focus to the trigger.

Evidence
  • BudgetPlanner/client/components/Layout/Layout.tsx:157-183

Recommendation. Extract the roving-focus logic from Codex Layout (onMenuKeyDown + focus effects) into the shared Menu component in AppBase and mirror it, so every app gets it for free.

7

No catch-all 404 route; unknown URLs render an empty shell

Medium
Ref P-08 Category UI/UX Also affects AppBase (Medium), Outfitter (Medium), Armory (Low), Sentinel (Medium)

Impact. AppBase, BudgetPlanner, Outfitter and Sentinel define no path="*" route. A mistyped or stale URL shows header, footer and backgrounds with a blank main area and no message. Codex renders a NotFoundPage inside Layout; Armory renders one but outside Layout (no header/nav/backgrounds), so even the two apps that have a 404 do not look alike.

Evidence
  • BudgetPlanner/client/app/routes.tsx:46-54

Recommendation. Add a NotFoundPage to AppBase, register path="*" inside the Layout route, and mirror. Move Armory's 404 route under the Layout child.

8

Port assignments collide and the AGENTS.md port table is wrong

Medium
Ref P-17 Category Docs Also affects AppBase (Low), Armory (Medium)

Impact. BudgetPlanner and Armory both default to PORT 3002, so running them side by side without env overrides fails. AppBase AGENTS.md states BudgetPlanner is 3001 (sharing with Codex); BudgetPlanner AGENTS.md says 3002; code says 3002. Playwright ports (3100-3104) are fine.

Evidence
  • BudgetPlanner/server/config.ts:102 process.env.PORT || '3002'
  • BudgetPlanner/AGENTS.md:11 "Default listen port in code is 3002"

Recommendation. Assign BudgetPlanner 3003 (currently unused) or another free port, update both AGENTS.md files and the README port tables, and add the full table to the org standards.

9

Button primitive leaks the variant prop to the DOM and loses its class on the anchor branch

Low
Ref A-BP-03 Category Logic/Bug Also affects this app only

Impact. BudgetPlanner rewrote Button so that {...buttonProps} still contains variant, which is emitted as a <button variant="accent"> attribute on every button. On the href branch the raw props (including className, possibly undefined) are spread after className={classes}, so an <Button href> would lose the composed btn classes entirely. No current caller uses href, so that half is latent; the attribute leak is live.

Evidence
  • BudgetPlanner/client/components/ui/Button.tsx:39-55 vs AppBase/client/components/ui/Button.tsx:39-58

Recommendation. Restore the AppBase version, which destructures variant/className/children before spreading.

Low

Impact. Every sibling logs request_failed with a requestId (server/http/requestId.ts + logger.ts) so a user-reported failure can be correlated. BudgetPlanner has neither: errorHandler.ts uses console.error and the response carries no id.

Evidence

  • BudgetPlanner/server/ has no http/requestId.ts or logger.ts

12

Auth state model differs per app (status values, admin flag name, /api/auth/me body)

Low
Ref P-06 Category Workflow Also affects AppBase (Medium), Codex (Medium), Outfitter (Medium), Armory (Medium), Sentinel (Medium)

Impact. AppBase/Outfitter/Sentinel use status "authenticated" + isAdmin; Codex/Armory use status "ok" + isCodexAdmin/isArmoryAdmin (+ apps[] in Codex); BudgetPlanner has no AuthContext. The /api/auth/me response body also differs ({userId,isAdmin} vs {authenticated,userId,isCodexAdmin,apps}). Anyone moving between codebases, or writing a shared component, must special-case every app. Codex/Armory also guard against stale refresh responses with a generation counter; the AppBase lineage does not, so a fast sign-out/sign-in can apply an out-of-order result.

Evidence
  • BudgetPlanner/client/components/Layout/Layout.tsx:1 uses @clerk/react useAuth directly; no app AuthContext

Recommendation. Define one AuthState in AppBase ({ status: loading|authenticated|unauthenticated|error, userId, isAdmin, apps? }) with the generation guard from Codex, and one /api/auth/me shape; mirror it.

16

Latent Modal bug: focus trap and Escape are never installed when a Modal mounts already open

Low
Ref P-14 Category Logic/Bug Also affects AppBase (Low), Codex (Low), Outfitter (Info), Sentinel (Low)

Impact. The shared Modal renders null until a "mounted" state flips, but the focus-trap/Escape effect depends only on [open]. If a Modal is mounted with open={true} on first render, the effect runs while the dialog is not yet in the DOM and never re-runs, so Escape and Tab-trapping are missing for that dialog. Today every caller in the affected apps keeps Modal mounted and toggles open, so it is latent; Outfitter already fixed it ([open, mounted]) and the fix was not upstreamed.

Evidence
  • BudgetPlanner/client/components/ui/Modal.tsx

Recommendation. Change the dependency array to [open, mounted] in AppBase Modal (as Outfitter did) and mirror to Codex, BudgetPlanner and Sentinel.

17

Route-level Suspense sits above Layout; no chunk-load recovery outside Codex/Armory

Low
Ref P-16 Category UI/UX Also affects AppBase (Low), Codex (Info), Outfitter (Low), Armory (Info), Sentinel (Low)

Impact. In AppBase, BudgetPlanner, Outfitter and Sentinel the Suspense fallback wraps <Routes>, so on first load users see a bare "Loading..." on the body gradient instead of the shell. More importantly, when a deploy replaces hashed chunks, a stale tab that navigates to a new lazy route throws ChunkLoadError; only Codex and Armory catch it and offer Retry/reload. Elsewhere it falls into the generic "Something went wrong" ErrorBoundary.

Evidence
  • BudgetPlanner/client/app/routes.tsx:40-45

Recommendation. Copy Codex ChunkErrorBoundary into AppBase, wrap the Suspense with it, and mirror. Consider moving Suspense inside Layout around <Outlet /> so the shell paints immediately.

18

Backend auth failure is silently treated as "signed out"; the auth error state is never shown

Info
Ref P-02 Category Error reporting Also affects AppBase (High), Codex (Medium), Outfitter (High), Armory (Medium), Sentinel (High)

In BudgetPlanner: Not affected in the same way: BudgetPlanner has no AuthContext and gates with Clerk hooks directly. Server-side user sync failures surface as 500 "Failed to sync user" on the first data call instead.

Impact. Every AuthContext computes status: "error" when GET /api/auth/me throws or returns 5xx, but no component in any app renders it. In AppBase, Outfitter and Sentinel, ProtectedRoute redirects on anything other than "authenticated", so a user who is signed in with Clerk but whose API is down is bounced to /sign-in with no explanation (Clerk then shows them as already signed in). In Armory, BuildStorageContext treats status !== "ok" as anonymous and quietly shows an empty library. Codex ignores the backend entirely for gating (Clerk <Show> only). Users cannot distinguish "not logged in" from "the server is broken".

Evidence
  • grep for status === 'error' | auth.error across all six clients: 0 matches.

Recommendation. Render the error state once, in Layout or the gate component: a banner "Could not verify your session" with a Retry that calls auth.refresh(). Gate components must branch on error separately from unauthenticated. Put this in AppBase ProtectedRoute and mirror it.

19

No shared typed API-error parsing; each app hand-rolls response.json() error extraction

Info
Ref P-05 Category Error reporting Also affects AppBase (Medium), Codex (Medium), Outfitter (Medium), Armory (Info), Sentinel (Low)

In BudgetPlanner: Has the best helper (ApiError with fields[]); candidate for upstreaming.

Impact. Servers consistently return { error: string } (good), but the template exposes no helper to read it. Only BudgetPlanner (ApiError + apiJson with field list) and Armory (parseApiError/readApiErrorMessage) have typed helpers; Codex, Outfitter, Sentinel and AppBase parse ad hoc in each page, with different fallback strings ("Request failed", "Failed to load fleet", statusText, etc.).

Evidence
  • BudgetPlanner/client/utils/api.ts:1-11, 123-141

Recommendation. Upstream BudgetPlanner's ApiError/apiJson (it already carries status and field names for form errors) into AppBase utils/api.ts and mirror. Standardise fallback copy.

20

Only BudgetPlanner is localised; the other five apps are hard-coded English

Info
Ref P-11 Category UI/UX Also affects AppBase (Medium), Codex (Low), Outfitter (Low), Armory (Low), Sentinel (Low)

In BudgetPlanner: The only localised app (16 files use useTranslation; locales en.json/de.json). Its LanguageSelector is not mirrored anywhere.

Impact. BudgetPlanner ships react-i18next with en/de bundles and a LanguageSelector in the user menu, persisted server-side. Switching to German there and then opening any sibling app returns you to English with no language control. For a platform that shares a login and a theme cookie, language is the obvious third shared preference and it is missing.

Evidence
  • BudgetPlanner/client/i18n/index.ts
  • BudgetPlanner/client/components/ui/LanguageSelector.tsx
  • BudgetPlanner/client/lib/locale.ts

Recommendation. Decide platform-wide: either add the i18n scaffold (provider, LanguageSelector, dal.locale cookie) to AppBase and mirror, or document that DAL apps are English-only and remove the selector from BudgetPlanner. If keeping i18n, share the locale via the same cookie mechanism as dal.theme.mode.

21

SelectDropdown has forked in four directions; improvements are not upstreamed

Info

Patterns worth adopting platform-wide

Good implementations that already exist in one app and would close several findings above if lifted into AppBase and mirrored.

  • Codex: ChunkErrorBoundary with Retry (client/app/routes.tsx) - recovers from stale chunks after deploys.
  • Codex / Armory: Full keyboard model for the user menu (roving focus, Home/End, focus return) and skip link.
  • Codex: LoadErrorBanner with Retry and role="alert"; ConfirmModal for destructive actions.
  • Armory: Session-expired modal driven by a global unauthorized event (Layout.tsx) - the only app that tells users why a request failed after a session lapse.
  • Armory: parseApiError/readApiErrorMessage and sendInternalError helpers.
  • BudgetPlanner: ApiError + apiJson with field-level error names; i18n scaffold; delete confirmation via glass Modal.
  • Outfitter: Modal effect dependency fix ([open, mounted]); SelectDropdown open-above logic and icon slot.
  • All: Server error bodies are uniformly { error: string } with X-CSRF-Error / code CSRF_INVALID; dependency versions are identical across all six package.json files; @theme, light-mode and UI-style token blocks are aligned apart from the Codex values in A-CX-04.

Suggested order of work

  1. Fix the two live BudgetPlanner bugs (theme keys A-BP-01, Clerk wildcard routes A-BP-02) and the Sentinel refresh gap (A-SN-01); they affect users today.
  2. Decide the error-presentation contract (P-01) and the auth error/gate behaviour (P-02, P-03), implement once in AppBase, then mirror. This is the bulk of the "one coherent platform" work.
  3. Bring AppBase up to the level of its own references (A-AB-01, P-07, P-08, P-09, P-16) so future apps start consistent.
  4. Sweep the low-severity drift (token values, SelectDropdown union, sign-out targets, ports/docs) in one mirror pass and extend the AGENTS.md checklist so it covers structure, not only tokens.
