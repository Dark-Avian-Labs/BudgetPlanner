Executive Summary

BudgetPlanner is in good overall shape for a security-sensitive household finance app. The core contracts stated in AGENTS.md are actually enforced in code: every plan sub-route passes through requirePlanAccess with correct owner/editor/viewer gating, all SQL uses parameterized better-sqlite3 statements, category and account IDs on entry writes are verified to belong to the same plan, invite acceptance requires a case-insensitive email match (403 otherwise), the owner cannot leave a plan, money is integer cents end to end, and shared/dueThisMonth.ts is genuinely the single source of month math for both client and server (both sides re-export it; no fork was found).

No Critical findings were identified. The single High finding is an environment-file fallback in server/config.ts that can silently load the wrong encrypted env file: a production host missing .env.production falls back to .env.development (dev Clerk keys, dev secrets) without any warning, and a bare node dist/server/index.js with unset NODE_ENV loads .env.production while all production-only safety checks are skipped.

The four Medium findings are: invite acceptance can silently overwrite an existing member's role — including demoting the plan owner, which strands the plan with no owner-role member; end_date is accepted on entry writes without any format validation even though credit money math depends on it; there are no integration tests covering the authorization matrix and invite flow; and the global CSRF-token middleware persists a session row for every request (including health checks and bot traffic), causing unbounded session-table churn.

The remaining findings are Low/Informational polish items: minor float rounding in amount input parsing, a synthetic fallback email that breaks invite matching for affected users, a dev-port default mismatch the repo itself warns about, small dead-code and i18n gaps, and UX refinements. Positive observations are listed at the end — notably strong CSRF handling with client retry, layered rate limiting, correct multi-row transactions, idempotent migrations, 192-bit invite tokens, and full en/de i18n key parity (124/124 keys).

HighDone Env-file fallback can silently load the wrong environment's secrets

server/config.ts:15-33, 96-100, 106-130

Description
resolveEnvFilePath() builds a prioritized list that always includes both env files as fallbacks. When NODE_ENV=production but .env.production is missing (e.g. bad deploy artifact), the server silently loads .env.development — development Clerk keys, dev session secret, dev DB paths — and continues to serve production traffic. Conversely, when NODE_ENV is unset (plain node dist/server/index.js, which is exactly what the start script runs), envFileByMode[''] is undefined, so the list becomes ['.env.production', '.env.development'] and production secrets are loaded while NODE_ENV later defaults to 'development' (line 100) — which skips the production-only guards: the default-SESSION_SECRET refusal (line 106), assertNotEncrypted for Clerk keys (lines 126-129), HSTS, and the SECURE_COOKIES/TRUST_PROXY invariant.

const prioritizedFiles = [
  envFileByMode[normalizedNodeEnv],
  '.env.production',
  '.env.development',
].filter(...);

for (const fileName of prioritizedFiles) {
  const candidatePath = path.join(projectRoot, fileName);
  if (fs.existsSync(candidatePath)) {
    return candidatePath;
  }
}

Impact
Production can run with development credentials (shared-login COOKIE_DOMAIN makes a dev Clerk instance in production especially dangerous), or a developer machine can run against decrypted production secrets with all production hardening disabled. Both failure modes are silent.

Recommendation
Load only the file matching NODE_ENV and fail fast (or at minimum log a loud warning) if it is missing. Never cross-fall-back between .env.production and .env.development. Also make the start script set NODE_ENV=production explicitly, as AppBase org standards already require.

MediumDone Invite acceptance overwrites existing membership roles — can demote the plan owner

server/routes/plans.ts:963-968 (accept), 798-817 (create invite)

Description
Invite creation does not check whether the target email already belongs to a member (or to the owner themselves), and acceptance blindly upserts the role:

db.prepare(
  `INSERT INTO plan_members (plan_id, user_id, role)
   VALUES (?, ?, ?)
   ON CONFLICT(plan_id, user_id) DO UPDATE SET role = excluded.role`,
).run(invite.plan_id, user.id, invite.role);

Invites can only carry editor or viewer roles. If the owner's own email is invited (the API allows it) and the owner accepts, their plan_members row is rewritten to editor/viewer while plans.owner_user_id still points at them. An existing editor accepting a stale viewer invite is silently downgraded the same way.

Impact
A plan can end up with no owner-role member: every owner-gated route (DELETE /:planId, member removal, invite management) returns 403 for everyone, permanently locking plan administration. This breaks the "owner cannot leave" invariant via a side door — the owner cannot leave, but they can accidentally stop being owner.

Recommendation
In the accept handler, refuse (or no-op) when an existing membership has role owner; consider also rejecting invite creation for emails that already match a member. Optionally use DO UPDATE ... WHERE plan_members.role != 'owner' as a defense-in-depth constraint.

MediumDone end_date accepted on entry writes without any validation

server/routes/plans.ts:597, 686-691 · server/lib/planValidation.ts:51-113 (no end_date rule) · shared/dueThisMonth.ts:21-29, 36-43, 69-74

Description
validateEntryBody() validates every other field but never checks end_date. The route stores any non-empty string verbatim:

// POST /:planId/entries (line 597)
typeof body.end_date === 'string' && body.end_date ? body.end_date : null,

The money math in shared/dueThisMonth.ts parses it with a strict YYYY-MM-DD regex and silently ignores anything that doesn't match. There is no SQL injection risk (fully parameterized), but the schema column has no CHECK either (server/db/appSchema.ts:22).

Impact
A malformed end_date (e.g. "03/2028" from a non-standard client, or a 64 KB junk string) is stored and then ignored: the credit never expires, the final_amount_cents installment never applies, and totals are silently wrong — the failure is invisible to the user. Data integrity for the one field that gates credit payoff math depends entirely on the browser's <input type="date">.

Recommendation
Add an end_date rule to validateEntryBody (reuse the same ^\d{4}-\d{2}-\d{2}$ shape plus a real-date check) and reject invalid values with 400, mirroring how due_month/due_year are handled.

InformationalDuplicate pending invites for the same email are allowed

server/routes/plans.ts:798-817

Description
POST /:planId/invites creates a new 14-day token on every call with no dedupe, so repeated clicks produce multiple simultaneously valid tokens for the same email. Each is individually revocable in the UI, and tokens are 192-bit random, so risk is negligible — this is mostly invite-list clutter.

Recommendation
On create, either return the existing pending invite for that email or revoke-and-replace it.

LowDone Failed entries-table migration would leave foreign_keys = OFF on the connection

server/db/appSchema.ts:189-231

Description
rebuildEntriesTable() disables foreign keys, runs the rebuild transaction, then re-enables them — but the re-enable is not in a finally block:

db.pragma('foreign_keys = OFF');
const tx = db.transaction(() => { /* rebuild */ });
tx();
db.pragma('foreign_keys = ON');

Impact
If the transaction throws, the exception propagates with FKs still off. Today the error would crash boot (no catch in server/index.ts), so practical exposure is small, but any future caller that catches the error would continue with referential integrity silently disabled for the process lifetime.

Recommendation
Wrap in try { ... } finally { db.pragma('foreign_keys = ON'); }.

LowDone parseAmountToCents uses float multiplication with edge-case rounding

client/lib/format.ts:41-47

Description
Storage is correctly integer cents, but the input parser converts through a float:

const value = Number(normalized);
if (!Number.isFinite(value) || value < 0) return null;
return Math.round(value * 100);

1.005 * 100 === 100.49999999999999, so "1.005" becomes 100 cents instead of the half-up-expected 101. Inputs with more than two decimals are also silently rounded rather than rejected ("1.239" → 124).

Impact
Worst case is a one-cent surprise for hand-typed three-decimal input — rare, but this is the entry point for all money in the app.

Recommendation
Parse the string digits directly (split on the decimal separator, reject >2 decimals, compute euros * 100 + cents in integers).

LowDone Synthetic fallback email <userId>@users.clerk breaks invite matching

server/middleware/auth.ts:45-54 · server/routes/plans.ts:956-959

Description
When session claims carry no email, the DB has none, and the Clerk API lookup fails, the user is persisted with a fabricated address:

return (await emailFromClerkApi(userId)) ?? `${userId}@users.clerk`;

Impact
Invite acceptance compares emails and returns 403, so such a user can never accept an invite — and because requireAuth only re-syncs when the resolved email differs from the stored one, a transient Clerk API failure on first sign-in can persist the fake address indefinitely. It is also displayed verbatim in the members list.

Recommendation
Treat "no resolvable email" as a retryable state (e.g. store NULL and re-attempt resolution on next request) instead of persisting a placeholder.

Informational"Current month" for auto-archival uses the server's local timezone

shared/planMonth.ts:9-11 · server/routes/plans.ts:101-104

Description
calendarMonth() uses new Date() in server-local time. Around month boundaries, a user whose timezone is ahead of or behind the server sees once entries archive/unarchive at the server's midnight, not their own. syncOnceArchiveState is correctly reversible (it unarchives when the state disagrees), so no data is lost — the flip is just mistimed by up to a day.

Recommendation
Acceptable for a single-household app; pin the server to the household timezone or derive the month from a client-supplied value if this ever matters.

MediumDone CSRF token middleware creates and persists a session row for every request

server/index.ts:124-127 (token middleware), 150-162 (/healthz & /readyz defined after it)

Description
A global middleware calls generateToken(req) on every request:

app.use((req, res, next) => {
  (res.locals as { csrfToken?: string }).csrfToken = generateToken(req);
  next();
});

csrf-sync stores the generated token in the session, which marks the session dirty, so despite saveUninitialized: false a session row is INSERTed for every cookie-less request — including load-balancer /healthz//readyz probes (routes are declared after this middleware), bots, and static asset requests that fall through to Express.

Impact
Continuous write churn on sessions.db and unbounded growth between the 15-minute cleanup sweeps; a health check every 10 s alone creates ~60,000 throwaway rows per week. Only /api/csrf actually needs the token.

Recommendation
Drop the global middleware and call generateToken(req) inside the /api/csrf handler (its only consumer, see server/routes/api.ts:12-15), or scope the middleware to /api after the health endpoints.

LowOnce-entry archival rescans every entry of the plan on each read and write

server/lib/planEntries.ts:9-42 · server/routes/plans.ts:101-104, 221, 602, 723, 751

Description
syncOnceArchiveState SELECTs all rows of the plan and updates them one-by-one inside a transaction on every plan GET (including viewer reads), entry create/patch, and reorder. It also means viewers trigger writes on read.

Impact
Negligible at household scale; noted because it runs on the hottest endpoint. The write-on-GET behavior is intentional per AGENTS.md ("auto-archived on plan load").

Recommendation
Replace the row-by-row loop with two set-based UPDATEs filtered by frequency = 'once' and the month comparison, and skip the call entirely when the plan has no once entries.

  • GoodMoney math is integer-cents everywhere with DB CHECK constraints (amount_cents >= 0), and shared/dueThisMonth.ts is the genuine single source of truth — client (client/lib/dueThisMonth.ts) and server (server/lib/dueThisMonth.ts) are pure re-exports; the cadence/final-installment rules are not forked.   • GoodCSRF protection is complete: synchronized tokens, sameSite: 'lax' + httpOnly cookies, secure cookies with an enforced TRUST_PROXY invariant in production (index.ts:49-51), and the client transparently refreshes and retries exactly once on token rejection (client/utils/api.ts:66-72).

  • GoodSecrets hygiene: .env.keys is gitignored, committed env files are dotenvx-encrypted, production asserts decryption succeeded (config.ts:126-129), and the server refuses to start with the default session secret in production.
